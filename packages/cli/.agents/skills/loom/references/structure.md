# Structure

This reference covers how to lay out a Loom application across files: the application module and the entry, the Command modules and the inputs they declare, and where plugins, shared options, views, and failure classes go.

## The application module and the entry

The application module (`src/application.ts`) declares the Application and exports it. The entry (`src/main.ts`) imports it and calls `run()`, and holds nothing else. `loom init` writes both in this shape.

- **Never call `run()` in the application module.** Every tool that loads the module expects it to declare and not run: the [assembly check](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/libs/testing.md#assertassembles) in a test, `loom init` when it writes the entry and the test, and `loom build`, which bundles the module as a second entry point beside the entry and loads it under Bun to read the [skills folder](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/toolchain/build.md#the-skills-folder).
- **Never import the entry**, from a test or from any other module. Importing it runs the application. A `run()` given no process handle binds the real process, so it reads the test runner's own argv and writes to its stdout.
- **Export exactly one Application.** `loom init` counts every exported value that is an Application, and for a module that exports two it writes no entry and no test. An Application stays an Application in every authoring state, so keep intermediate values, such as the `configured` value below, unexported.
- **Build the Application when the module loads.** Do not hide it in a function that the entry calls. `loom build` reads `skills()` only from what runs while the module loads.
- **A test imports the application module.** It passes the Application to `assertAssembles` and runs it on a `mockProcess` handle, never on the real process. Keep the assembly test `loom init` writes at `src/application.test.ts`: it is the one check that fails CI for a fault that only the assembled application reveals. It does not run a declared default or an implied value through its validator, so also run the application at least once on a `mockProcess` handle. [Testing](testing.md) covers the rest.

## The application module's contents

Write the application module in this order, because each step types the next:

1. `const configured = new Application(name, { ... })` with every plugin, view override, translator, and Application-level extension value.
2. Each `globalOption()` call, then any root-local `option()`.
3. When the root has children, the [Application registration](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/commands.md#modular-authoring): `declare module '@loomcli/core'` with `Register.environment` set to `EnvironmentOf<typeof configured>`. Register this configured value, never the finished Application, because the finished one imports the Commands that read the registered types. To type an action's `invoke`, also set `Register.paths` to `PathsOf<typeof app>` of the finished Application from step 4: Command paths are read only where a call reads them, so this one registration of the finished value is not circular, under [Typed paths](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/invocation.md#typed-paths).
4. The exported Application: `configured.command(...)` for each child, then `rows()` or `result()` and `action()` for a root that runs.

Keep one registration per TypeScript project. A second application, an example, or a test with its own registration needs its own `tsconfig.json`.

[`configuration()`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/config.md#the-plugin-and-its-values) returns the plugin and a provider, `{ plugin, values }`. It reads JSON alone unless you pass a reader in `formats`: `toml` from `@loomcli/plugins/config/toml`, `yaml` from `@loomcli/plugins/config/yaml`. A `file` that names a TOML or YAML extension without its reader throws at `configuration()`, so pass the reader of each format your operators may write, under [Readers](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/config.md#readers). When a Command opts in to `values`, call `configuration()` in a module of its own, such as `src/config.ts`, so the application module imports the plugin and the Command imports the provider, and no Command imports the application module. Under a supervisor, where nobody reads `-v`, pass `strict` to `configuration()`, `true` or a list of key paths, so a broken setting fails the run with code 2 instead of being dropped, under [The strict setting](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/config.md#the-strict-setting).

## Commands and files

Start from the scaffold: one application module with an inline root action. Split files when a second Command arrives or when an action grows.

- **One module per Command, by convention.** Put each Command in `src/commands/<name>.ts`, which exports the Command value, as the [`get` Command](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/commands/get.ts) of the jsonkit example does. A Command module imports `@loomcli/core`, its own action, extension values from plugin subpaths such as `@loomcli/plugins/help/extension`, and shared declarations. It never imports the Application. Its global option types come from the registration.
- **A group imports its children.** A group's module imports each child and attaches it with `command()`. Mirror a deep path in folders, such as `src/commands/cache/clear.ts` for `cache clear`. A small subtree whose Commands exist only under one parent can stay in one module, as [`stats.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/commands/stats.ts) holds `stats`, `depth`, and `max`. Nothing in Loom reads the file layout: the graph is the `command()` calls, and their order is the order every listing shows.
- **One placement per Command value.** A Command value attaches at one point in the graph. A Command that belongs under two parents comes from a function that returns a new value for each placement.
- **A second name is an alias.** Keep a former or commonly guessed name working with `alias()` on a Command or `aliases` on an option, which no listing shows. Declare a short form operators should learn, such as `ls` for `list`, with [`visibleAlias()`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/commands.md#visible-aliases) or [`visibleAliases`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#visible-option-aliases), which help, the man page, completion, and the manifest show beside the canonical name. Either kind routes to the one member, and neither is a second Command or option.
- **Extract an action to test it.** Put an extracted action in its own module, such as [`src/actions/get-value.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/actions/get-value.ts), typed `ActionHandler<typeof get>` through `import type` of its Command. Keep the Command's initializer ending in `.action(getValue)`, and derive an `extend()` value from the finished Command instead, under [Modular authoring](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/commands.md#modular-authoring). A unit test calls the extracted action with [`actionContext`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/libs/testing.md#actioncontext). An inline action has no public path to a unit test.
- **A root with arguments and children.** A Command with an action, the root included, may declare arguments and hold children, so a root that takes arguments, like the [textstat example](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/textstat/src/application.ts)'s, can install plugin Commands such as `help({ command: true })`, `completion()`, or `mcp()`; textstat installs `completion()`. A plain word that is exactly a child's name or alias routes into that child. Any other word fills the first argument, and once a word fills an argument no later word routes. An operator passes a child's name as an argument after `--`, as in `textstat -- completion`, and a child added in a later release shadows that word as an argument. A group, a Command with children and no action, declares no arguments.
- **Share steps as functions.** A step that several actions repeat, such as reading and parsing a document, is a plain function in its own module. Type its parameter as the part of the action context it reads, such as `Pick<Log, 'debug'>`, so a test passes only that part.

## A Command's inputs

Each setting's doc comment states its rules. Choose among them by what the operator types:

- **Check a value with a validator.** Declare `validate` on the input, and start from the [catalog](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/libs/validators.md#catalog) in `@loomcli/validators`, such as `integer()`, `path()`, `bytes()`, `host()`, or `date()` with the `layouts` operators type. Add a rule to a catalog validator with [`pipe()`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/libs/validators.md#pipe) rather than writing its parse again.
- **An option given more than once.** A second occurrence of a string option fails as a repeat. Declare `multiple: true` to collect every occurrence as a list, or [`lastWins: true`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#last-occurrence-wins) to keep the last, so a wrapper script or a shell alias puts a default first and the operator's later value replaces it.
- **Several words to one option.** Declare [`arity`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#option-value-arity) for a fixed count of separate words per occurrence: `{ arity: 2, type: 'string', validate: integer() }` reads `--point 3 4` as `[3, 4]`, typed as a tuple. No question answers an arity option.
- **Options that depend on each other.** `exclusive()`, `oneRequired()`, and `requiredTogether()` constrain a group, and [`requires('password', 'user')`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#a-one-way-requirement) refuses `--password` without `--user` while it accepts `--user` alone. A default never counts as supplied.
- **Words after `--`.** The first bare `--` ends option parsing, and the words after it fill the Command's arguments, so `rm -- -draft.txt` takes a file name that starts with a hyphen. A Command that forwards words to another program declares [`.passthrough()`](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#passthrough) before `action()`, and its action reads them untouched in `passthrough`. Without the mode, the action has no `passthrough`.
- **A list before a fixed argument.** Required arguments may follow a variadic one, as in `copy <src...> <dest>`. They fill from the end of the line, and the variadic takes the words between.
- **What Tab offers for a value.** Mark an option with `completionInput` or an argument with `completionArgument` from `@loomcli/plugins/completion/extension`, with `extensions`, `directories`, or `none`; an argument may also take `commands`. For values your code knows, such as task ids, define a named completer in `completion({ values: { task: ... } })` and name it with `values: 'task'`. A closed-set validator already completes its set, under [Value hints](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/completion.md#value-hints) and [Named completers](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/completion.md#named-completers).
- **An input a question asks for.** Declare `required: 'non-interactive'` on it, so a run that cannot ask fails before the action, and link the question to it, under [Middleware and actions](middleware-and-actions.md).

## Plugins

Install every plugin in the `plugins` list of the Application constructor. The list order is the [installation order](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/plugin-contract.md#identity-and-installation), and it decides several things at once:

- The middleware chain runs in list order, so the plugin listed first wins a tie. List `help()` before `version()`, so `--help --version` prints help.
- A plugin's view overrides resolve after the Application's own and before later plugins'.
- Plugin Commands attach to the root ahead of the application's own Commands, and listings show them first.

An application that needs its own middleware or lifecycle hook writes a plugin of its own. Give it a folder, such as `src/plugins/<name>/`, with an entry module that exports the factory with an annotated return type and a middleware module that the entry loads with `import()`, as the [explain example's plugin](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/explain/src/plugin.ts) does. Name its identity under the application's name, such as `notes/timing`. [Middleware and actions](middleware-and-actions.md) says when a plugin of your own is the right choice.

A skill the application installs for agents can carry a generated reference for each Command: name the Commands with `commands`, such as `[[]]` for the whole application, on the skill or on a `{ name, commands }` entry beside a `folder`. Add per-Command guidance with `skillCommand`, under [Command references](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/skills.md#command-references).

## Options shared across Commands

- **A value every action reads** is a global option: `globalOption()` on the Application before its first `command()` or `action()`. A global option has no presence rule and cannot be a content option, under [Global options](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/commands.md#global-options).
- **An input several Commands declare,** especially a required one or a content input, is one settings constant declared locally on each Command. The jsonkit example's [`src/document-input.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/document-input.ts) exports `documentInput`, typed with `satisfies ContentOption`, and each document Command calls `.option('file', documentInput)`. A Command that reads no document declares no `--file`.
- **Several inputs that Commands share together,** or a group over them such as `exclusive('json', 'yaml')` or `requires('password', 'user')`, are one [option set](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/options.md#sharing-options): `optionSet({ ... })` in a module of its own, with its group calls chained on it, and `.options(set)` on each Command that reads them. Each entry takes what `option()` takes, and the action's types are those of the same `option()` calls. A set never inherits, so a parent that applies it gives its children nothing: apply it on every Command that reads the options. A Command may still add its own options and a group that names a set's option beside its own. The set's order is its record's key order, which help shows. The jsonkit example's [`src/json-layout.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/json-layout.ts) exports `jsonLayout`, `--compact` and `--indent` with an exclusive group, and each Command that prints JSON calls `.options(jsonLayout)`. Keep the settings constant for a single option.
- **A typed value derived from global options,** such as a database pool or a session, is a [provider](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/providers.md). Commands that share providers share one `uses` constant, because a child inherits nothing from its parent.

## Views and failures

- **Views.** By convention, keep `View` values in `src/views.ts`; nothing in Loom reads the file. A result's views belong in its Command's `result()` or `rows()` record, and a pack view there is replaced by name through `views()`. A replacement for a declared view or a failure class's view goes in the Application's `views` list as `override(key, view)`, as the [jsonkit example's application](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/application.ts) overrides `FatalError`.
- **Failure classes.** Declare an application's own failure class, a `FatalError` subclass, with a static `code` and `exitCode` when it needs them, in the module of the code that throws it, as the jsonkit example's `PathNotFoundError` sits in [`resolve-path.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/resolve-path.ts). Keep a translator beside the class it produces, as [`translators.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/translators.ts) holds `InvalidJsonError` and `invalidJson`, and list the translator in the Application's `translators`. [Failures](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/core/failures.md) states the class contract.
- **Lists that several Commands repeat,** such as the jsonkit example's manifest failure lists in [`failures.ts`](https://github.com/dbtlr/loomcli/blob/v0.20.0/examples/jsonkit/src/failures.ts), are shared constants, because a Command's [manifest failure list](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/plugins/manifest.md#manifest-failures) inherits nothing from its parent.

## The toolchain configuration file

A package that keeps the conventions needs no `loom.config.json`. Add one beside `package.json` only to move a path, under [The configuration file](https://github.com/dbtlr/loomcli/blob/v0.20.0/docs/toolchain/build.md#the-configuration-file).

- `paths.application` and `paths.entry` follow `paths.source` unless they are set themselves, and every path resolves against the package directory.
- The application module and the entry need different base names. A `node` or `bun` bundle names each output file for its module alone, so an entry at `src/cli/application.ts` beside an application module at `src/application.ts` fails the build.
- `loom init` reads the configured paths when it writes the scaffold files, but it writes each scaffold file once and never updates it. When you move `paths.source` later, update `tsconfig.json`'s `include`, the linter's file globs, and the `check` script's lint target yourself.
- The agent skills stay at `.agents/skills/`, and `package.json`, `tsconfig.json`, and the linter's file stay at the package root, whatever the file holds.
